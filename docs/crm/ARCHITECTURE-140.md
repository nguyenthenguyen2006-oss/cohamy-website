# Cohamy - architecture

Existing Next.js 16.3.5 / TypeScript / PostgreSQL application retained. PGlite is a single-process LOCAL QA adapter. Public website and blog ownership unchanged.

- Applicant identity lives in partner_applications + applicant_sessions, independently of users/memberships/sessions. Verification alone never grants CRM/portal membership.
- Approval locks the application, requires verified SUBMITTED status, bounds invitation scope, grants organization/user/membership/assignment once, then writes immutable history/audit and in-app notification in the same transaction. Retry requires the exact approval fingerprint.
- Workspace preferences/drafts/filters/bookmarks belong to a user. Drafts have typed allowed fields and optimistic versions. Search and recent/pinned/notifications recheck current entity access. Sharing a filter never shares data.
- Private file storage uses DB bytea, so files are included in database backups and commit with immutable document versions. Download authenticates membership and rechecks source entity. MIME magic, bounded bytes, no public URLs, attachment disposition and no-store apply. Storage can be extracted behind the upload/download service later without changing ACL semantics.
- data_jobs provides PREVIEW -> QUEUED -> RUNNING -> SUCCEEDED/FAILED, user idempotency keys, scope fingerprint, leased claim and atomic import. Import never writes until confirmation; errors at write time roll back all rows. Export is bounded to 5000 and safe string XLSX cells. Outputs recheck user identity, role, assignment fingerprint and individual source records. after() is a response-after kick; durable worker must be supervised for restart recovery. It is not a scheduler guarantee.
- Dealer addresses/cart are organization/account scoped. Cart is a draft, not a priced order. Support threads are organization scoped; internal messages cannot be read or created by portal users.
- The partner library checks published status, effective/expiry windows, organization and dealer role before returning documents; immutable latest file versions drive own-user acknowledgements and onboarding progress. Catalog reads are persisted; a draft cart never counts as a first commercial request.
- Dealer owners can lock only their own staff within the fixed role ceiling. Locking revokes all staff sessions in the same transaction; unlocking requires fresh login and never restores an old token.
- Relationships use versioned reason/tag dictionaries, multiple tags with AND filtering before pagination/export, contact preferences and active SKU interests. Opportunities keep immutable actor/time/stage history; losing a task does not mark a customer LOST. Append-only visits link a private photo source and enforce exact retry/current partner scope.
- Tasks use version locks, checklist completion guard and acyclic same-record dependencies. Dependency edits/completion/reopen are serialized using the dependency-table lock plus task row locks. Opposite edits in PostgreSQL cannot commit a cycle. Care schedules/rules/SLA use transactional immutable outcomes with current membership and source rechecks; the managed worker recovers due work after actual process death.
- Commercial requests/orders use immutable policy, request and order versions plus append-only events. Portal staff proposals require exact owner approval before explicit Cohamy submission; exception confirmation follows a different configured approver. Confirmed snapshots freeze price/unit/address/source while delivery/payment remain independent and unposted. No enabled real D05 policy is seeded.
- Stock, delivery documents, AR/AP and consignment ledgers are still separate work. Website intake and confirmed order state never fabricate their balances or posting events.
